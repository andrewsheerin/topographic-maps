# Scientific and domain integrity

The user is a PhD environmental engineer. **Scientific correctness is theirs, not yours.**
You implement; you do not decide. This rule exists because a plausible-looking wrong number is
more dangerous than an obvious error, and because scientific mistakes propagate silently into
results that get published or used.

## Never decide these — always escalate to `project-management/DECISIONS.md` (Needs you)

- Unit systems and conversion factors
- Formulas, coefficients, and empirical constants
- System boundaries, functional units, allocation methods
- Default values and assumptions for missing data
- Emission factors, characterization factors, impact methods
- Statistical treatment: which test, how outliers are handled, how uncertainty propagates
- Rounding and significant figures in anything reported

If a value is needed and not specified, **do not pick a reasonable-looking one.** Do not source it
from memory or the web and proceed. Stop and ask. "I found a commonly cited value of X" is a
proposal, not a decision.

## Implementation requirements

1. **Units are explicit in the code.** Variable names or type annotations carry units:
   `mass_kg`, `energy_mj_per_kg`. Never a bare `mass`. Conversions happen in one place, never
   inline at the point of use.
2. **Every constant is traceable.** A magic number in a formula gets a named constant with a
   comment naming its source and units. If the source is "the user told me on <date>," write that.
3. **Constants live in one module**, not scattered across the codebase. Changing a factor should be
   a one-line edit in a known place.
4. **Calculation logic gets tests at every tier, including L1.** This is the one place where L1
   does not get to skip tests. Test against a worked example the user has verified.
5. **Never silently coerce.** If input data is missing, out of range, or in unexpected units, fail
   loudly. Do not substitute a default, do not interpolate, do not drop the row.

## When you spot a possible error

Flag it, show the reasoning, propose the correction, and wait. Do not "fix" a formula you believe
is wrong — you may be missing domain context that makes it correct.

## Dataset provenance (any external or scientific dataset, GIS included)

Every dataset that enters `data/` gets an entry in `data/DATA_SOURCES.md` **in the same commit**,
covering: source and citation; version or retrieval date; license and usage terms; spatial
reference (CRS/datum) where applicable; temporal coverage; units; nodata conventions; and known
limitations or uncertainty.

- **Transformation lineage:** every derived dataset records what it came from and the script that
  produced it. If it can't be regenerated by running code in the repo, it isn't done.
- **CRS is never assumed.** Reprojection is explicit, logged in lineage, and uses a stated
  transformation. Mixed-CRS operations are a bug, not a warning.
- **Nodata is never silently filled.** Gaps propagate visibly or the handling rule comes from the
  user (that's a decision, not a default).
- **Reproducibility:** pin the versions of anything whose output feeds reported numbers.
